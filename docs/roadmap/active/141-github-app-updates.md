# Обновления TTSBard через GitHub Releases

## Цель

Пользователь узнаёт о новой стабильной версии TTSBard, читает описание релиза
и выбирает, когда обновиться. GitHub Releases служит источником метаданных
и файлов для Windows x64.

Проверка, уведомления и установка уже реализованы; их принятый результат
сохранён в Outcome. Реализация этапа 2 начата 2026-11-18 через ZCode Bridge.
Его требования заменяют правила этапа 1 о запуске, расписании, повторах
и отображении результата проверки.

## Этап 1. Проверка и уведомление

- В «Настройки → Общие → Обновления» показывать текущую версию, время последней
  успешной проверки, кнопку «Проверить сейчас» и переключатель автопроверки.
  Для новой версии показывать её номер, Markdown-блок
  с описанием релиза и ссылку «Открыть на GitHub».
- Перенести отображение текущей версии из сайдбара над кнопкой «Выход»
  в карточку «Обновления».
- При включённой автопроверке запрашивать последний стабильный релиз при первом
  запуске и затем по выбранному интервалу, включая работу в трее. В селекторе
  «Проверять каждые» доступны интервалы от 1 до 7 дней с шагом в день,
  по умолчанию 1 день. При выключенной автопроверке селектор недоступен,
  выбранное значение сохраняется, а ручная проверка по-прежнему работает.
  Отсчитывать интервал от последней успешной проверки, включая ручную.
  Сохранять её время между запусками и пересчитывать срок при смене интервала.
  Если срок прошёл, пока приложение было закрыто, проверить при запуске.
- Использовать GitHub API для получения версии, описания и ссылки. Сравнивать
  версии по SemVer. При ошибке фоновой проверки повторить запрос с задержкой.
  Ошибку ручной проверки показывать в карточке, сохраняя сведения о последнем
  найденном релизе.
- При обнаружении новой версии показать компактное уведомление «Доступна
  версия X» у правого края под заголовком обычного и компактного окна и под
  панелью режима «Моно». Использовать форму системных уведомлений и нейтральный
  фон текущей темы. Уведомление располагается поверх содержимого и ниже
  модальных диалогов и системных уведомлений.
  «Подробнее» открывает «Настройки → Общие» сразу на карточке «Обновления»
  с описанием релиза; карточка прокручивается с `scroll-margin-top`, чтобы
  бабл не закрывал её заголовок. Из компактного окна и «Моно» сначала
  открывается обычное окно. Бабл остаётся без таймера и виден, когда
  главное окно открыто.
- Крестик скрывает бабл для этой версии, в том числе после повторной проверки
  и перезапуска. Карточка продолжает показывать релиз. Более новая версия
  снова вызывает бабл. Бабл также исчезает, когда версия уже установлена.

## Установка из приложения

- Дополнить существующую публикацию по тегу: сохранить NSIS-установщик и
  отдельный `ttsbard.exe`, подписывать установщик ключом обновлений Tauri
  и публиковать рядом его отдельную подпись `.exe.sig`. Версию, описание и
  список файлов Бард получает через GitHub Releases API.
  Публиковать стабильный релиз после загрузки файлов. Закрытый ключ хранить
  в GitHub Actions Secrets, открытый встроить в приложение.
- Для NSIS-установки проверять подпись Tauri перед запуском. Кнопку «Обновить»
  разместить по центру под прокручиваемым описанием релиза, без подписи.
  В уведомлении остаются «Подробнее» и крестик.
- По кнопке «Обновить» открывается модальное окно с прогрессом загрузки.
  Загрузку отменяют кнопка «Отмена» и крестик. Escape и клик по подложке
  оставляют загрузку активной. После
  успешной загрузки проверить подпись, сохранить состояние редактора и
  позицию окна и сразу запустить установщик. Перед запуском ничего не
  останавливается и не отменяется: если установщик не запустился,
  приложение остаётся рабочим и попытку можно повторить; штатное
  завершение сервисов выполняет сам выход процесса.
  После установки открыть новую версию. При ошибке загрузки или подписи
  оставить приложение запущенным и дать повторить попытку.
- Для отдельного `ttsbard.exe` оставить проверку и переход к релизу для ручной
  замены файла. Пользователям сборок без встроенного установщика обновлений
  понадобится один ручной переход на версию с этой функцией.
- При выпуске встроенной установки обновить руководства пользователя на
  [русском](../../ru/user/guide.md) и [английском](../../en/user/guide.md).
  Указать, что кнопка «Обновить» доступна в Барде, установленном через
  `*_x64-setup.exe` (NSIS). Для отдельно скачанного `ttsbard.exe` обновление
  выполняется вручную через GitHub, даже если на компьютере установлена
  другая копия Барда.
- Возможность «Установить при выходе» рассмотреть отдельно после проверки
  обновления по кнопке.

### Настройка ключей подписи (выполнить до первого релиза с установкой)

Ключи настраиваются один раз в GitHub Actions.

1. Сгенерировать пару ключей подписи обновлений:
   `npm run tauri signer generate -- -w ~/.tauri/ttsbard-updater.key`.
   Получатся два файла:
   закрытый ключ и `<ключ>.pub`.
2. Закрытый ключ — в GitHub Secrets репозитория `ttsbard/TTSBard`:
   `TAURI_SIGNING_PRIVATE_KEY` (содержимое файла ключа) и
   `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (пароль; может быть пустым, если
   ключ сгенерирован без пароля). Старые имена `TAURI_PRIVATE_KEY` /
   `TAURI_KEY_PASSWORD` в workflow не используются и могут быть удалены.
3. Содержимое публичного `.pub` добавить в переменную GitHub Actions
   `TAURI_UPDATER_PUBLIC_KEY`. Сборка подставляет его во временный конфиг Tauri.
   Подробности в [документации сборки](../../development/github-actions-build.md#подпись-обновлений).
4. Проверка: сборка по тегу с заданным секретом должна приложить к релизу
   `*-setup.exe` и `*-setup.exe.sig`; в установленном приложении карточка
   «Обновления» покажет кнопку «Обновить» для новой версии.

## Этап 2. Проверка при запуске и прозрачный результат (в работе)

### Настройки и запуск

- Разделить автоматические проверки на две независимые настройки в карточке
  «Настройки → Общие → Обновления»:
  - «Проверять обновления при запуске приложения» — включено по умолчанию
    для новых настроек;
  - «Проверять обновления во время работы каждые» — выключено по умолчанию
    для новых настроек; рядом селектор от 1 до 7 дней, по умолчанию 1 день.
    При выключенной настройке селектор недоступен, выбранный интервал
    сохраняется.
- Проверка при запуске — одна асинхронная попытка на запуск процесса,
  независимо от времени предыдущей проверки. Она не задерживает открытие
  приложения. Возврат из трея, вызов горячей клавишей, открытие окна
  или карточки настроек не считаются новым запуском и не инициируют
  эту проверку повторно.
- Обе настройки работают независимо: только запуск, только расписание,
  оба варианта или только ручная проверка. Кнопка «Проверить сейчас»
  доступна при любом сочетании настроек, кроме времени выполнения проверки.
- Миграция прежней настройки не требуется: пользователь рассматривает
  это как новый функционал. Новые настройки без сохранённого значения
  получают указанные дефолты; последующий выбор пользователя сохраняется.

### Расписание и ошибки

- После любой завершённой проверки, включая неудачную и ручную, следующую
  периодическую попытку планировать через выбранный интервал. Учитывать
  время последней попытки между запусками; при смене интервала пересчитывать
  срок. Если стартовая проверка выключена, а периодическая включена,
  просроченную периодическую проверку выполнять при запуске; при отсутствии
  предыдущих попыток также выполнить одну проверку.
- Удалить пятиминутные повторы после ошибок. Каждая неудачная проверка
  завершается записью уровня `warn` в лог и результатом в карточке.
  Если включена только проверка при запуске, автоматический повтор возможен
  лишь при следующем запуске процесса. Ручная проверка остаётся доступной.
- Если обе настройки включены и при запуске подошёл срок периодической
  проверки, выполнять одну общую попытку. Исключить параллельные проверки
  и вторую автоматическую попытку сразу после успешной или неудачной первой.
  При выключенной периодической настройке не выполнять проверки по расписанию,
  включая работу в трее.

### Результат в карточке обновлений

- Показывать результат последней завершённой попытки и её время одинаково
  для стартовой, периодической и ручной проверки: установлена последняя
  версия, доступна новая версия либо проверка не удалась.
- Для ошибки показывать спокойную плашку в карточке с базовой формулировкой:
  «Не удалось получить информацию о последней версии с GitHub».
  Ошибка автоматической проверки не вызывает отдельное всплывающее окно,
  бабл ошибки или запрос подтверждения.
- Результат остаётся в карточке до следующей завершённой проверки.
  Успешная проверка заменяет предыдущую ошибку; неудачная не должна
  показывать, что установлена последняя версия.
- Разделить результат последней попытки и сведения о ранее найденном релизе.
  Ошибка не стирает известное обновление, его описание или время последней
  успешной проверки. Если обновление было найдено раньше, предложение
  обновиться и плашка неудачной свежей проверки могут отображаться вместе.
  Время неудачной попытки не подменяет время последней успешной проверки.
- При реализации обновить русские и английские строки и пользовательские
  руководства. Для UI-проверки применить
  [правила проверки UI](../../development/ui-guidelines.md); временный отчёт
  и скриншоты хранить в `.work/ai/`, путь к отчёту указать в локальном task.

### Критерии приёмки этапа 2

- На новых настройках включена только проверка при запуске. Проверить все
  четыре сочетания галочек, сохранение настроек и недоступность селектора
  при выключенном расписании.
- При включённой проверке при запуске на каждый новый процесс приходится
  одна стартовая попытка; вызов из трея или по горячей клавише, открытие окна и настроек её
  не повторяют. При обеих выключенных настройках автоматических проверок нет.
- При включённых обеих настройках запуск не создаёт две проверки, даже
  если периодическая уже просрочена. Проверить взаимодействие с ручной
  проверкой во время автоматической попытки без дублирования запросов.
- После сетевой ошибки, тайм-аута, ограничения GitHub или некорректного
  ответа есть запись в логе и плашка, нет повторов через пять минут.
  Следующая периодическая попытка происходит через выбранный интервал,
  в том числе после ошибки и при работе в трее; без расписания её нет.
- Проверить срок после успешной и неудачной проверки, смены интервала
  и перезапуска; при выключенной стартовой проверке просроченное расписание
  и первый запуск с включённым расписанием выполняют одну попытку.
- В карточке проверить результаты «актуальная версия», «доступно обновление»
  и «ошибка», переход от ошибки к успеху и совместный показ ранее найденного
  обновления с новой ошибкой. Время последней успешной проверки при ошибке
  не меняется. Проверить русский и английский языки, обе темы и узкое окно.

## Этап 3. Хранение состояния проверок в «Данных программы» (реализован)

- В `settings.json` оставить три пользовательские настройки: проверку при
  запуске (`startup_check_enabled`), периодическую проверку
  (`periodic_check_enabled`) и её интервал (`check_interval_days`).
- Хранить в `updates/state.json` внутри выбранного каталога «Данные программы»
  последний найденный релиз (`last_release`), время успешной проверки
  (`last_check_at`), время и ошибку последней попытки
  (`last_attempt_at`, `last_attempt_error`) и версию, для которой закрыли
  уведомление (`dismissed_version`). Записывать состояние атомарно.
- Начинать с пустого состояния при отсутствии или повреждении файла.
  Для этой версии миграция не требуется. Прежние поля состояния в
  `settings.json` игнорируются, сохранённые настройки расписания применяются.
- Сохранить поведение этапа 2 и контракт IPC. После перезапуска карточка
  читает сохранённый релиз, а срок следующей периодической проверки считается
  от последней завершённой попытки. Ошибка проверки сохраняет результат
  последней успешной проверки. Закрытие уведомления действует для той же версии
  после перезапуска.

При смене «Данных программы» карточка и планировщик переключаются на новый
каталог в текущем сеансе. Уже начатая проверка сохраняет результат в исходном
каталоге. Нативная приёмка этого сценария в установленном приложении остаётся
открытой.

### Проверка этапа 3

- Убедиться, что проверка пишет состояние в выбранный каталог «Данные программы»,
  а в секции `updates` файла настроек сохраняются только три настройки.
- Проверить повторный запуск после успешной и неудачной попыток, восстановление
  карточки и срока следующей проверки, а также сохранение отметки о закрытом
  уведомлении.
- Проверить запуск с отсутствующим и повреждённым файлом состояния. Приложение
  применяет сохранённые настройки расписания и может выполнить новую проверку.

## Outcome

Пользователь принял проверку обновлений и уведомления 2026-11-17.
Ручная проверка сообщает об актуальной версии, ошибке или доступном
релизе. Фоновая проверка работает по интервалу 1–7 дней, сохраняет
результат между запусками и показывает найденную версию в трёх режимах
главного окна. «Подробнее» открывает карточку с описанием релиза,
а крестик запоминает закрытие для конкретной версии.

Пользователь принял интерфейс встроенной установки. В установленной через
NSIS версии кнопка «Обновить» появляется для доступного подписанного релиза.
Отмена, ошибка подписи и переход к установке проверены на UI-стенде.

2026-11-18 пользователь подтвердил нативный смоук встроенного обновления
подписанным установщиком на Windows («работает»). Условия: локальная NSIS-
сборка с внутренней версией 1.8.1; те же байты установщика опубликованы под
именем `TTSBard_1.8.2_x64-setup.exe` с подписью под это имя как обычный
последний релиз 1.8.2 в ttsbard/TTSBard; подписи сверены независимо, включая
имена файлов; SHA256 установщика совпал, скачанные байты и `/releases/latest`
проверены. Границы: внутренняя версия осталась 1.8.1, поэтому переход между
двумя разными версиями и обновление до релиза, собранного GitHub Actions,
остаются непроверенными; сценарии этапа 2 (стартовая проверка, расписание,
ошибки, языки и темы) этим смоуком не считаются покрытыми. Тестовый релиз
1.8.2 и его файлы удалены в тот же день по просьбе пользователя, тег сохранён.

## Критерии проверки

- Ручная и фоновая проверки корректно обрабатывают актуальную версию, новый
  стабильный релиз и недоступность GitHub. Расписание сохраняется при
  перезапуске и работает в трее.
- Смена интервала пересчитывает срок проверки. Выключение автопроверки
  сохраняет выбранный интервал и оставляет ручную проверку доступной.
- Закрытие бабла сохраняется для найденной версии. Новый релиз снова показан
  баблом в каждом режиме главного окна; «Подробнее» открывает карточку так,
  что бабл не закрывает её заголовок.
- Проверить русские и английские состояния карточки и бабла по
  [правилам проверки UI](../../development/ui-guidelines.md), включая слой
  бабла над панелями и под модальными диалогами и обе темы.
